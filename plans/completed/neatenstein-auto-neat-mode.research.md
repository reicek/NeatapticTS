# Neatenstein Auto / NEAT Mode Gap Analysis

## Question

Why is Neatenstein auto / NEAT mode not working? Specifically:

- Why does selecting `humanMode: 'auto'` in the UI have no effect on gameplay?
- Why does the NEAT progressive evolution (enemy population + main-agent champion) never progress?
- Where is the gap between the intended NEAT progressive evolution and the current behavior?

## Evidence

### Gap 1: The `humanMode: 'auto'` flag is a dead field — the worker never reads it

- **browser-entry.ts:560** posts `humanMode: getHumanMode()` into the render state.
- **renderer/frame.ts:70** declares `humanMode?: 'auto' | 'human'` in `NeatensteinRenderState`.
- The JSDoc on `humanMode` says "downstream consumers (including the arms-race configuration) enable replay-driven selection pressure" — but no consumer exists.
- **display.worker.ts**: grep for `humanMode` returns ZERO matches. The worker processes `simState` messages (line 1130-1347) but never reads the `humanMode` field.
- The player is ALWAYS controlled by human input: `InputRouter.getSnapshot()` → `forwardWorkerInput()` → `gameTick(gameState, tickInput, ...)` (worker line 1253).
- There is NO code path where a NEAT-evolved network generates movement/look/fire decisions for the player.

**Confidence: 0.97** | Provenance: static-code (browser-entry.ts, renderer/frame.ts, display.worker.ts)

### Gap 2: The evolution harness is completely disconnected from the live game loop

- `advanceWave()` (host/waves.ts) — evolves enemy MLP population, spawns next wave. NEVER called from the live game; only referenced in its own definition and test file.
- `runArmsRaceGeneration()` (harness/arms-race.ts) — runs a generation of the arms race. NEVER called from the live game; only mentioned in a COMMENT in browser-entry.ts line 287.
- `runMainAgentGeneration()` / `runMainGeneration()` (harness/main-agent.ts, main-runner.ts) — runs the main-agent evolution. NEVER called from the live game.
- `createMlpEnemyPopulation()` — only used in tests and imported as a type in waves.ts.
- The live game spawns enemies via `spawnWaveTick()` (host/game/waves.ts:161), called from `updateEpisode()` (host/game/episode.ts:255), called from `gameTick()` (host/game/tick.ts). This path has NO evolution logic — it just spawns one enemy at a time at map edges.

**Confidence: 0.97** | Provenance: static-code (host/waves.ts, harness/arms-race.ts, harness/main-agent.ts, host/game/waves.ts, host/game/episode.ts, host/game/tick.ts, display.worker.ts)

### Gap 3: The main-agent champion is a placeholder genome with null nodes/connections

- `harness/arms-race.ts:184-198` — `createMainSnapshot()` creates a "lightweight placeholder genome" with `nodes: new Array(nodeCount).fill(null)` and `connections: new Array(connectionCount).fill(null)`.
- JSDoc: "The champion is a lightweight placeholder genome sized from the generation seed. Future slices will replace this with real NEAT selection once the main-agent lifecycle and topology constraints are wired into the harness."
- `harness/main-runner.ts:228-244` — `createMainGenome()` DOES call `buildMainAgentEmbryo()` from the real NGE pipeline, but the result is cast to `Genome` and never used to control the player.

**Confidence: 0.95** | Provenance: static-code (harness/arms-race.ts, harness/main-runner.ts)

### Gap 4: The harness episode is a fake/simulated stand-in using RNG, not real gameplay

- `harness/main-runner.ts:309-332` — `runEpisode()` JSDoc: "This is a lightweight headless stand-in for the full game episode."
- All combat metrics (survivalTicks, damageDealt, kills, damageTaken, aimMissRate) are generated by `seedrandom` RNG, NOT by actually playing the game.
- The fitness signals don't reflect real gameplay performance — they're deterministic random numbers keyed on variant ID and seed.
- Separately, `host/game/episode.ts:373` has another `runEpisode()` that DOES play the game (via `updateEpisode` loop) using a "deterministic damage bot" — but this is also never called from the evolution harness or the live game loop.

**Confidence: 0.93** | Provenance: static-code (harness/main-runner.ts, host/game/episode.ts)

### Gap 5: Enemy neural networks are never activated in the live game — enemies always use BFS

- `scripts/enemy-controller.ts:328` — `createEnemyControllerState()` initializes all enemies with `weights: undefined`.
- `scripts/enemy-controller.ts:397` — `updateControlledEnemy()`: `const weights = isRespawn ? undefined : previousOrDefault.weights` — weights are ALWAYS undefined.
- The MLP re-ranking path (line 655: `weights !== undefined`) is NEVER reached because weights are never set to actual MLP weights.
- `harness/enemy-mlp.ts:167-202` — `activateMlp()` function exists and is imported by enemy-controller.ts (line 31), but it's only called when weights are non-undefined, which never happens.
- Enemies always use pure BFS distance map navigation — no neural network at all.

**Confidence: 0.96** | Provenance: static-code (scripts/enemy-controller.ts, harness/enemy-mlp.ts)

### Gap 6: The `generation` field in GameState is initialized to 1 and never incremented

- `host/game/state.ts:107` — `generation: 1` in initial game state.
- Grep for `generation` in tick.ts and display.worker.ts returns ZERO matches (no increment, no read).
- The evolution harness (arms-race, main-runner) maintains its own generation counters in the headless simulation, but these are never synced back to the live game's `GameState.generation`.

**Confidence: 0.94** | Provenance: static-code (host/game/state.ts, host/game/tick.ts, display.worker.ts)

## Architecture Summary

The Neatenstein demo has TWO completely separate systems:

1. **Live game** (host/game/, worker/display.worker.ts): Human-controlled player + BFS-navigated enemies. No NEAT evolution. The `generation` field is stuck at 1. Enemies spawn continuously via `spawnWaveTick()`. The `humanMode: 'auto'` selector is forwarded to the worker as a dead field.

2. **Evolution harness** (harness/): Standalone headless simulation with fake episodes (RNG-based metrics), placeholder genomes (null nodes/connections), and no integration with the live game loop. The harness runs its own generation counters but never syncs them back. `advanceWave()` and `runArmsRaceGeneration()` are never called from the live game.

The `humanMode: 'auto'` selector exists in the UI but has no functional effect — it's forwarded to the worker as a dead field that is never read.

## Decision

The root cause is architectural: the evolution harness was built as a parallel, standalone system and was never wired into the live game loop. Six integration points are missing:

1. **Worker must read `humanMode`** and branch to a neural-network controller instead of forwarding human input.
2. **`advanceWave()` must be called from the live game** when a wave is cleared (or on a generation timer).
3. **Enemy weights must be populated** from the MLP population (via `createMlpEnemyPopulation()` / `activateMlp()`) instead of always being `undefined`.
4. **The main-agent champion genome** must be a real evolved network, not a null-filled placeholder, and must be used to control the player in auto mode.
5. **The harness episode** must run real gameplay (or at minimum use the live game's `runEpisode`) instead of RNG-based fake metrics.
6. **`GameState.generation` must be incremented** when a generation completes, and the evolution harness's generation counter must sync to it.

## Risks

- **Performance**: Running real episodes for fitness evaluation (instead of RNG) will be computationally expensive. The cadence helpers (host/game/cadence.ts) estimate generations-per-minute, and the target minimum is `NEATENSTEIN_MIN_GENERATIONS_PER_MINUTE` (from constants). Real gameplay episodes may not meet this target without optimization (e.g., headless fast-forward, worker-side simulation).
- **Determinism**: The live game uses `createGameRng(seed)` for spawn positions; the harness uses `seedrandom` for episode metrics. These two RNG systems must be reconciled for reproducible fitness evaluation.
- **Worker threading**: The evolution harness runs on the main thread; the live game runs in a Web Worker. Bridging the two requires careful message-passing design to avoid blocking the render loop.
- **Episode design**: The current `runEpisode` (host/game/episode.ts) uses a "deterministic damage bot" that ignores controller inputs. To evaluate a NEAT network, the episode must accept controller inputs from the network's output layer. This is a non-trivial refactor.
- **Backward compatibility**: The human-played mode must remain functional. The `humanMode` selector is the intended switch point, but the branching logic doesn't exist yet.

## Addendum: Fire-gate wiring and training/inference mismatch (2026-08-10)

### Question

Does the soft fire gate (`applyFireGate` with hysteresis 0.15/0.18) actually work in live auto-mode gameplay? Specifically:

- Does `buildAutoTickInput` in `display.worker.ts` pass the sensor vector and `fireGateState` to `networkOutputToTickInput`?
- Is the fire gate bypassed anywhere?

### Evidence

- `display.worker.ts:1445-1463` — `buildAutoTickInput` extracts sensors, activates the champion network, and calls `networkOutputToTickInput(raw, { state: fireGateState, enemyVisible: sensors[ENEMY_VISIBLE_SENSOR_INDEX] ?? 0 })`. Both the mutable hysteresis state and the current enemy-visible sensor value are passed correctly.
- `neat-io-config.ts:171-198` — `networkOutputToTickInput` applies `applyFireGate(fireGate.state, fireGate.enemyVisible, out[3])` when `fireGate` is provided; otherwise it falls back to raw `out[3] > 0`.
- `neat-io-config.ts:114-134` — `applyFireGate` mutates `state.fireActive` based on the 0.15/0.18 thresholds and returns `rawFireOutput > 0` only when the gate is open.
- Two production fitness-evaluation paths call `networkOutputToTickInput(out)` **without** the fire-gate config:
  - `harness/main-runner.ts:334` inside `runEpisode()` (headless variant fitness).
  - `worker/eval.worker.ts:81` inside `runFitnessEpisode()` (dedicated NEAT evaluation worker).
- `scripts/enemy-navigation.ts:482` sets `sensors[12] = 1` only when a visible enemy exists; otherwise the sensor is `0`. The value is therefore binary, so the 0.15–0.18 hysteresis band is never exercised in practice — the gate acts as a simple visibility switch rather than a true hysteresis gate.

### Decision

The live auto-mode path (`buildAutoTickInput`) is correctly wired and is not bypassed. The fire gate **is** bypassed in the training/fitness evaluation paths, which use raw fire output. This creates a train/runtime behavior mismatch: champions are selected under raw-fire semantics but play under gated semantics. If the gate is meant to be part of the learned policy, the fitness functions in `main-runner.ts` and `eval.worker.ts` must also thread the fire-gate state and `enemyVisible` sensor through `networkOutputToTickInput`.

### Risks

- **Train/runtime mismatch**: A champion that fires aggressively (or not at all) when no enemy is visible may score well during evolution but look broken when the gate suppresses its fire in live gameplay.
- **Hysteresis band is dead**: Because `enemyVisible` is binary, the 0.15/0.18 band never prevents oscillation; any rapid on/off fire behavior is due to network output jitter, not the hysteresis.
- **Gate state lifetime**: `fireGateState` is module-level in `display.worker.ts` and reset on `init` (line 1589). It persists across ticks and waves but does not carry across worker restarts.

**Confidence: 0.94** | Provenance: static-code (`display.worker.ts`, `neat-io-config.ts`, `main-runner.ts`, `eval.worker.ts`, `enemy-navigation.ts`), verified by `boundary-mapper` scout.

## Confidence

Overall investigation confidence: **0.95** — all findings are based on direct static-code evidence from the actual source files. No runtime/behavioral evidence was gathered (no test runs, no browser sessions), but the code paths are unambiguous: the harness is never called, the worker never reads `humanMode`, and enemy weights are always `undefined`.

### Decision

The requested audit categories break down as follows:

- **Sensor module responsibility split**: Moving `extractSensors` out of `scripts/enemy-navigation.ts` is a structural change that affects three consumers plus tests and README routing.

## Addendum 3: 15-input vision bypass in live auto-mode gameplay (2026-08-10)

### Question

Why isn't the `extractSensors` 15-input expansion being used during live auto-mode gameplay? Specifically:

- Trace the actual call path from `gameTick` to `buildAutoTickInput`.
- Find any old 12-input or omniscient enemy detection that bypasses the new vision system.

### Evidence

- **Call-path direction is reversed from the wording.** `gameTick` in `examples/neatenstein/browser-entry/host/game/tick.ts` is a pure reducer that **consumes** a `GameTickInputSnapshot` (interface lines 75-99). It is called by the worker at `display.worker.ts:1751` and never calls `buildAutoTickInput`. `buildAutoTickInput` in `display.worker.ts` is an **upstream producer** of that snapshot (lines 1445-1463).
- **Actual live auto-mode path (when a champion exists):**
  `display.worker.ts` `simState` handler (lines 1648-1751)
  → selects `tickInput`
  → if `humanMode === 'auto' && championMainNetwork` (line 1671)
  → `buildAutoTickInput(network, gameState, wallMap, NEATENSTEIN_MAP_SIZE)` (lines 1673-1678)
  → `extractSensors(state, flatMap, mapSize)` (line 1451)
  → `network.activate(sensors)` (line 1452)
  → `networkOutputToTickInput(raw, { state: fireGateState, enemyVisible: sensors[ENEMY_VISIBLE_SENSOR_INDEX] ?? 0 })` (lines 1459-1462)
  → passed to `gameTick(gameState, tickInput, collisionMap, timestepMs)` (line 1751).
- **15-input vector is wired correctly.** `NEATENSTEIN_MAIN_NEAT_INPUTS = 15` in `harness/neat-io-config.ts:19`. `extractSensors` in `scripts/enemy-navigation.ts:448-511` creates `new Array(15).fill(0)` and populates:
  - player sensors: health, ammo, angle, x, y (5);
  - nearest visible enemy: bearing, distance, health (3) plus `enemyVisible` (index 12) and `inFiringArc` (index 13) (2);
  - wall raycasts: N/E/S/W (4);
  - `lastShotHit` (1).
    Total = 15.
- **The live bypass is `buildFallbackAutoTickInput`.** In `display.worker.ts:1497-1553`, when `humanMode === 'auto'` but `championMainNetwork` is `null` (before the first champion is evolved), the worker builds the tick input with an exploration AI that:
  - iterates `state.enemies` directly;
  - selects the nearest active enemy by raw Euclidean distance;
  - ignores `VISION_RANGE_CELLS` (15 cells) and wall line-of-sight;
  - fires whenever the chosen enemy is within `NEATENSTEIN_FALLBACK_FIRE_ARC` of the facing direction and a cooldown interval has elapsed.
    This matches the historical omniscient 12-input enemy-detection behavior described in `plans/neatenstein-firing-sensor-system.research.md`.
- **No remaining production 12-input champion path.** The genome-extinction guard at `display.worker.ts:1656-1669` clears `championMainNetwork` whenever `lastChampionInputCount !== NEATENSTEIN_MAIN_NEAT_INPUTS` (15). The only remaining literal "12" references are:
  - `ENEMY_VISIBLE_SENSOR_INDEX = 12` in `harness/neat-io-config.ts:54` — a valid index inside the 15-input layout;
  - `__testOnlySetChampionInputCount` in `display.worker.ts:2022-2024` and its test in `display.worker.test.ts:3367-3395` — backward-compat extinction-guard test hooks;
  - the active plan prose at `plans/neatenstein-auto-neat-mode.plans.md:40` still describes "~12 inputs" even though the implementation uses 15.
- **Enemy AI itself remains omniscient, but outside the player's vision system.** `scripts/enemy-controller.ts` computes yaw and flanking targets directly from `gameState.player.position` and rebuilds a BFS distance map rooted on the player cell every tick. This is a separate issue, not a bypass of the player's 15-input vision system.

### Decision

- The 15-input `extractSensors` vector **is** used in live auto-mode gameplay whenever `championMainNetwork` is present. It is only unused in the pre-champion fallback.
- The requested `gameTick → buildAutoTickInput` edge does **not exist** and is architecturally undesirable: `gameTick` consumes a `GameTickInputSnapshot`, while `buildAutoTickInput` produces one. Any future refactor should preserve this producer/consumer separation.
- The actual live bypass is the chicken-and-egg fallback `buildFallbackAutoTickInput` in `display.worker.ts`, which intentionally uses omniscient enemy detection until the first champion is evolved. This is the only place where old 12-input-style behavior still runs in production.
- The stale "~12 inputs" prose in the active plan and the 12-input test hooks are documentation/test debt, not a runtime bypass.

### Risks

- **Train/runtime mismatch in the pre-champion window:** The fallback fires without the soft fire gate (`FIRE_GATE_HYSTERESIS_LOW/HIGH`) and without the `enemyVisible` sensor, while the champion path uses both. Pre-champion auto gameplay therefore behaves differently from champion-driven auto gameplay.
- **Permanent fallback risk:** If the arms-race/eval-worker wiring never produces a champion (`championMainNetwork` stays `null`), auto mode will remain stuck on the omniscient fallback forever.
- **Deadlock tension:** Making `buildFallbackAutoTickInput` vision-aware (reusing `findNearestVisibleEnemy` / `hasLineOfSight`) would make the first wave harder to clear, potentially extending the chicken-and-egg deadlock. Any change here must balance vision fidelity against bootstrapping the first champion.
- **Plan drift:** The active plan still says "~12 inputs" and lists only 11 sensor channels. Future slices may size networks incorrectly if the prose is not updated.

**Overall confidence: 0.92** | Provenance: direct static-code evidence from `display.worker.ts`, `host/game/tick.ts`, `harness/neat-io-config.ts`, and `scripts/enemy-navigation.ts` with unambiguous branch logic. No runtime/browser session evidence was gathered, but the call graph is explicit.

## Addendum 4: 15-input sensor support for exploration and kiting (2026-08-11)

### Question

Does the current 15-input `extractSensors` vector in `examples/neatenstein/scripts/enemy-navigation.ts` provide enough information for the NEAT main agent to (a) behave sensibly when no enemy is visible (exploration), and (b) kite enemies by maintaining a preferred distance and relative angle?

### Evidence

- Current sensor layout (indices 0–14):
  - [0–4] player health, ammo, absolute look angle, x, y
  - [5] nearest visible enemy bearing relative to the player, normalized to `[0, 1]`
  - [6] nearest visible enemy distance divided by `VISION_RANGE_CELLS` (15)
  - [7] nearest visible enemy health ratio
  - [8–11] world-cardinal wall raycasts N/E/S/W
  - [12] `enemyVisible` binary
  - [13] `enemyInFiringArc` binary (within ±30°)
  - [14] `lastShotHit` binary
- `findNearestVisibleEnemy` returns `null` when no active enemy is within `VISION_RANGE_CELLS` or line-of-sight is blocked; in that case enemy sensors `[5]`, `[6]`, `[7]`, `[12]`, `[13]` are zeroed (`scripts/enemy-navigation.ts:466-484`).
- The fallback AI (`buildFallbackAutoTickInput`) uses scan-turn + forward movement when no enemy is visible and turns toward a visible enemy when one appears (`display.worker.ts:1504-1557`).
- Tests (`enemy-navigation.test.ts:748-756`, `907-924`) assert the zeroing behavior for no-enemy, beyond-vision, and blocked-LOS cases.
- `NEATENSTEIN_MAIN_NEAT_INPUTS = 15` caps the vector length; any addition requires displacing an existing sensor or increasing the constant (`harness/neat-io-config.ts:19`).

### Decision

1. **Exploration (no-enemy-visible):** Partially supported. The agent knows it cannot see an enemy (`enemyVisible = 0`) and can sense local walls (cardinal rays) and its absolute position/heading. However, it lacks a dedicated exploration signal such as time-since-last-enemy, last-known-enemy bearing decay, or player-relative forward obstacle distance. It can wall-follow but has no memory or sweep-state to drive systematic search.
2. **Kiting:** Core geometry is present (distance `[6]`, relative bearing `[5]`, fire-ready arc `[13]`). Health/ammo state supports engagement decisions. However, the agent cannot predict enemy motion (no velocity), cannot sense if it is cornered (no backward/forward ray aligned with the look direction), and has no preferred-range error signal (distance saturates at the 15-cell vision cap, while bolt max range is ~30 cells).
3. **Recommended changes (if input count must stay 15):**
   - Replace the single normalized bearing `[5]` with a `sin(bearing), cos(bearing)` pair to eliminate the 0/1 discontinuity and give the network a smooth two-dimensional angle encoding. This costs one extra input, so offset by either:
     - Dropping `lastShotHit` `[14]` (one-tick delayed reward, weak for closed-loop control), or
     - Dropping one of the absolute position sensors `[3]`/`[4]` unless the map has strong spatial structure.
   - Add a `dashReady` or `dashCooldownRatio` sensor to support kiting bursts (costs one input; candidate displacement: `lastShotHit`).
   - Add a `forwardWallDistance` raycast aligned with the player's look angle (costs one input; candidate displacement: one world-cardinal ray or `lastShotHit`).
4. **Recommended changes if input count can expand:**
   - Increase `NEATENSTEIN_MAIN_NEAT_INPUTS` to ~18 and add: `sin/cos bearing` (2), `timeSinceEnemySeenMs` or `lastKnownBearingDecay` (1), `forwardWallDistance` (1). This avoids displacing useful existing sensors.
5. **No code changes needed immediately:** The current vector is sufficient for a first reactive policy. Add sensors only if learned behavior shows the agent fails to explore or kite.

### Risks

- **Bearing discontinuity:** The `[0, 1]` wrap-around at ±π can make learning turn decisions harder near the boundary; `sin/cos` encoding is preferable.
- **World-locked raycasts:** Cardinal wall distances do not rotate with the player; the network must implicitly combine `angleRad` + rays, increasing learning burden.
- **Input budget lock-in:** The network input size is a genome/structure constant; changing it later requires re-evolving champions and updating tests, harness config, and any serialized genomes.
- **Kiting range mismatch:** The vision cap (15 cells) is half the bolt max range (~30 cells); a network may close distance too eagerly because distance saturates before the agent is at a safe kiting range. A preferred-range or raw-distance signal normalized by bolt range would be more useful.
- **Behavioral validation gap:** Tests assert sensor values but not policy quality. Any sensor change should be accompanied by a fitness/evaluation slice that checks exploration/kiting behavior.

### Confidence

**Overall confidence: 0.88** | Provenance: direct static-code evidence from `enemy-navigation.ts`, `neat-io-config.ts`, `display.worker.ts`, and test assertions, plus an independent `implementation-pattern-scout` review. No runtime/browser policy evidence was gathered.

## Addendum — Hero kiting behavior (2026-08-11)

### Correction to prior finding

The earlier "Gap 5" analysis above claimed that `buildFallbackAutoTickInput` in
`display.worker.ts` ignores `VISION_RANGE_CELLS` and wall line-of-sight. A
fresh read of the current source shows that is **not** the case:

```ts
const visibleEnemy =
  wallMap !== null
    ? findNearestVisibleEnemy(state, wallMap, NEATENSTEIN_MAP_SIZE)
    : null;
```

(`display.worker.ts:1513-1516`). The fallback **does** use the same
vision-limited target selection as the NEAT sensor path. The source of the
"charge straight at enemies" behavior is therefore not omniscient targeting,
but the **unconditional forward movement** returned by the fallback.

### Current movement logic

- `buildAutoTickInput()` (`display.worker.ts:1451-1469`) delegates movement to
  the champion network. It has no hand-coded distance policy, so kiting can
  only emerge from evolution/fitness.

- `buildFallbackAutoTickInput()` (`display.worker.ts:1504-1557`) always returns
  `move: { x: 0, y: 1 }`. It turns toward the nearest visible enemy and fires
  when the enemy is within `NEATENSTEIN_FALLBACK_FIRE_ARC` (±π/6) and the
  cooldown interval has elapsed. Because it never sets `y < 0`, the hero
  closes to contact range before any other behavior takes over.

- `networkOutputToTickInput()` (`harness/neat-io-config.ts:171-198`) already
  maps `move.y = tanh(outputs[1])`, so the output layer can express
  forward/back/strafe. The NEAT path is mechanically capable of kiting.

- Movement is applied in `host/game/movement.ts` and `host/game/tick.ts`:
  `move.y > 0` means forward relative to the player's current yaw, and
  `move.y < 0` means backward. With the player facing the enemy,
  `move.y = -1` is a direct backpedal away from the target.

### Key ranges

| Constant                                    | Value | Implication                                      |
| ------------------------------------------- | ----- | ------------------------------------------------ |
| `VISION_RANGE_CELLS`                        | 15    | Current max LOS acquisition distance             |
| `NEATENSTEIN_BOLT_MAX_RANGE_CELLS`          | 30    | Player bolts can hit farther than current vision |
| `ENEMY_CONTROLLER_FIRE_RANGE_CELLS`         | 8     | Enemies cannot fire back at 15–20 cells          |
| `NEATENSTEIN_CONTACT_RANGE_CELLS`           | 0.5   | Contact damage only at melee range               |
| `NEATENSTEIN_PLAYER_SPEED_CELLS_PER_SECOND` | 6     | Player outruns enemies (2.5 cells/s)             |

A 15–20 cell standoff is tactically sound: it is out of enemy bolt range,
well inside player bolt range, and only reachable while the enemy is visible.

### Proposed kiting behavior

Add distance-aware movement to `buildFallbackAutoTickInput()`:

```ts
const KITE_MIN_RANGE_CELLS = 15; // backpedal if closer
const KITE_MAX_RANGE_CELLS = 20; // approach if farther
const KITE_ACQUIRE_RANGE_CELLS = NEATENSTEIN_BOLT_MAX_RANGE_CELLS; // 30
```

1. Acquire the nearest visible enemy within `KITE_ACQUIRE_RANGE_CELLS` and
   LOS (a fallback-specific helper, so `VISION_RANGE_CELLS` and sensor
   normalization remain unchanged for the NEAT path).
2. If no target is visible, keep the existing scan-turn + move-forward
   behavior.
3. If a target is visible:
   - Turn toward it (same capped `lookDelta`).
   - Set `move.y` by distance:
     - `< KITE_MIN_RANGE_CELLS` → `-1` (backpedal)
     - `> KITE_MAX_RANGE_CELLS` → `+1` (approach)
     - in band → `0` (hold distance; optionally small `move.x` strafe)
   - Fire exactly as before when on-target and off cooldown.

Because the player yaw tracks the enemy, `move.y = -1` moves directly away
while firing, satisfying "backpedal while firing". When the enemy drops
beyond 20 cells, `move.y = +1` re-engages, satisfying "approach only when out
of range".

### NEAT path

No code change is required in `buildAutoTickInput()` if the fitness function
rewards kiting. Sensor index 6 already carries normalized enemy distance.
Recommended fitness additions:

- bonus for damage dealt while player health is high,
- reward for keeping the nearest enemy in the 15–20 cell band,
- penalty for contact damage / close proximity.

### Risks

1. **Do not change `VISION_RANGE_CELLS` globally.** It normalizes the NEAT
   distance sensor. Use a fallback-only acquisition helper.
2. **Wall/corner traps.** Backpedalling can pin the hero in narrow corridors;
   consider a wall-behind safety check.
3. **Multiple enemies.** Kiting away from the nearest enemy may lead into
   others; target selection may need a wider safety heuristic.
4. **Boundary oscillation.** Add a small deadband (±0.5 cells) around the 15
   and 20 thresholds.
5. **Test drift.** Existing fallback tests likely expect `move.y = 1`.
   Update `display.worker.test.ts` with red tests at 10, 17, and 25 cells.
6. **NEAT learning time.** Without explicit fitness pressure, the champion
   network may keep charging forward because it still scores kills.

### Confidence

**Overall confidence: 0.91** | Provenance: direct static-code read of the
fallback and I/O mapping functions, plus the constants governing movement,
bolt range, enemy range, and collision. The proposed thresholds rely on the
recorded constant values and have not been validated by a live browser
session.

## Addendum — Fallback AI no-enemy exploration behavior (2026-08-14)

### Question

Why does the Neatenstein fallback AI spin in circles when no enemies are
visible, and what exploration behavior should replace the current scan-turn?

### Evidence

**Root cause: constant forward movement plus a fixed turn rate creates a
small circle.**

`buildFallbackAutoTickInput()` (`display.worker.ts:1504-1557`) has the
following defaults when no enemy is visible:

```ts
let lookDelta = NEATENSTEIN_FALLBACK_TURN_RATE; // Math.PI / 12 ≈ 15°/tick
...
return {
  move: { x: 0, y: 1 },
  lookDelta,
  fire,
  dash: false,
};
```

The player moves forward at `NEATENSTEIN_PLAYER_SPEED_CELLS_PER_SECOND = 6`
cells/s while yawing at a fixed rate of
`NEATENSTEIN_FALLBACK_TURN_RATE = π/12` radians per
`NEATENSTEIN_FIXED_TIMESTEP_MS = 16` ms tick.

| Derived quantity   | Value                | Formula                                     |
| ------------------ | -------------------- | ------------------------------------------- |
| Angular velocity ω | ≈ 16.36 rad/s        | (π/12) / 0.016                              |
| Linear velocity v  | 6 cells/s            | `NEATENSTEIN_PLAYER_SPEED_CELLS_PER_SECOND` |
| Circular radius r  | ≈ 0.37 cells         | v / ω                                       |
| Full-rotation time | ≈ 0.384 s (24 ticks) | 2π / ω                                      |

The resulting circle is barely larger than the player's collision radius
(`NEATENSTEIN_PLAYER_RADIUS_CELLS = 0.25`), so the fallback AI spins almost
in place instead of covering the map. This matches the observed "spins in
circles" symptom.

**Current code path when an enemy _is_ visible.**

The same function already turns toward the nearest visible enemy and fires
within `NEATENSTEIN_FALLBACK_FIRE_ARC` (±π/6) on a 25-tick cooldown. The
no-enemy branch is the only one that retains the unconditional forward +
fixed-turn default.

**Reusable exploration primitives already exist in the repo.**

- `findNearestVisibleEnemy()` and `extractSensors()` in
  `scripts/enemy-navigation.ts` provide LOS + 15-cell vision queries and
  BFS distance maps.
- `castRayDDAFromFlatMap()` from `renderer/raycast.ts` can probe open space
  ahead of the player (used by the renderer for wall/edge distance).
- `buildEnemyDistanceMap()` / `findBestNavigationStep()` give grid-aware,
  wall-correct pathfinding toward any target cell.
- `updatePlayerMovement()` and `resolveWallCollision()` in
  `host/game/movement.ts` rotate the `move: {x, y}` vector by player yaw and
  resolve wall collisions, so any proposed `move` vector is interpreted
  relative to the current facing direction.

**asciiMaze exploration patterns to mirror.**

The asciiMaze example already implements several exploration strategies in
`mazeMovement/policy/mazeMovement.policy.ts` and
`mazeMovement/mazeMovement.services.ts`:

- `applyMazeMovementEpsilonExploration()` — ε-greedy random valid move.
- `applyMazeMovementForcedExploration()` — random valid move after a stall
  counter exceeds `NO_MOVE_STREAK_THRESHOLD`.
- `applyMazeMovementProximityGreedy()` — distance-map descent toward a goal.
- `randomMazeMovementUnit()` — mulberry32-style seeded PRNG with
  `Math.random()` fallback.
- Visit-count tracking in the maze movement store rewards exploration of
  less-visited cells.

### Decision

The no-enemy-visible branch should **stop turning while moving forward** and
adopt an **exploration policy** that covers the map until an enemy enters
vision. Three candidate strategies are proposed, ordered from simplest to
most sophisticated.

#### Option A — Direction persistence with wall-bounce (recommended)

Add module-level fallback-exploration state in `display.worker.ts` (or a
small helper module):

```ts
const EXPLORATION_WALL_DISTANCE_CELLS = 2.0; // react to wall this far ahead
const EXPLORATION_SCAN_RATE = 0; // no idle scan while moving
const EXPLORATION_TURN_ON_BOUNCE = Math.PI / 2; // 90° when blocked
const EXPLORATION_CORNER_TOLERANCE = 0.25; // deadband around ray hit
```

1. When no enemy is visible, set `move: { x: 0, y: 1 }` and `lookDelta = 0`
   (move straight in the current yaw).
2. Use `castRayDDAFromFlatMap()` to sample distance to the first wall cell
   directly ahead.
3. If the sampled distance is below `EXPLORATION_WALL_DISTANCE_CELLS`, pick
   a new yaw that points into the most open direction. A simple heuristic:
   - Cast three short probes at yaw, yaw + π/2, yaw − π/2.
   - Choose the direction with the longest open distance.
   - If all are blocked, turn 180°.
4. Only change yaw once per bounce event; otherwise keep `lookDelta = 0`.

**Pros:** trivially deterministic, no PRNG state, naturally follows corridors,
covers large open areas, very small code footprint.
**Cons:** can get stuck in local loops (e.g., a square corridor); periodic
scan turns may still be useful to break deadlocks.

#### Option B — Deterministic Levy walk with seeded PRNG

Reuse the `randomMazeMovementUnit()` mulberry32 helper to derive a
pseudorandom target yaw from `state.seed` and `fallbackTickCounter`. The
fallback picks a new target yaw every `LEVY_STRAIGHT_TICKS` ticks and moves
straight between picks.

```ts
const LEVY_STRAIGHT_TICKS_MIN = 30; // ~0.5 s
const LEVY_STRAIGHT_TICKS_MAX = 90; // ~1.4 s
const LEVY_BOUNCE_DISTANCE_CELLS = 1.5;
```

1. Seed the PRNG with a deterministic mix of `state.seed` and
   `fallbackTickCounter` so replays are identical for the same seed.
2. When the current straight run expires or a wall is hit, draw a new random
   target yaw and clamp the turn over one or two ticks.
3. Between picks, move straight (`lookDelta = 0`, `move.y = 1`).

**Pros:** covers space efficiently, breaks circular trajectories,
fully deterministic if seeded from `state.seed`.
**Cons:** requires importing or duplicating a PRNG; more parameters; may
still collide with walls if the bounce check is too coarse.

#### Option C — Visit-count map coverage

Maintain a low-resolution visit grid (`NEATENSTEIN_MAP_SIZE` cells, or a
coarser 8× downsample). Use `buildEnemyDistanceMap()` from the player's
cell and score each candidate direction by how many fresh cells it would
uncover. This mirrors the asciiMaze visit-bonus approach.

**Pros:** thorough coverage, escapes local loops, can deliberately sweep
unseen parts of the map.
**Cons:** largest implementation cost; needs per-tick visit-grid update;
memory/state overhead; overkill until the other fallback gaps (kiting, fire
hysteresis) are addressed.

**Recommended path: implement Option A first**, then consider Option B as a
follow-up if Option A's local-loop behavior is unsatisfactory. Option C is a
longer-term enhancement only after the fallback is otherwise stable.

### Interaction with the kiting addendum

The kiting addendum above proposes distance-aware movement when an enemy _is_
visible. These two changes compose cleanly:

- Enemy visible → use kiting (Option A in the kiting addendum).
- No enemy visible → use exploration (Option A/B/C here).
- Both keep `move: { x: 0, y: * }` and use `lookDelta` only for aiming or
  collision avoidance, so the control surface stays the same.

### Risks

1. **Determinism.** Neatenstein gameplay is currently deterministic for a
   given seed. Option A preserves that; Option B must derive PRNG state from
   `state.seed` to keep replays stable. Option C adds mutable visit-grid state
   that must be reset on episode restart.
2. **Wall/corner traps.** Bounce logic can oscillate in tight corners if the
   raycast threshold is too small or the turn angle is too symmetric. Add a
   small deadband and prefer the more-open of left/right when both are free.
3. **Test drift.** `display.worker.test.ts` fallback tests currently expect
   `move.y = 1` and likely assume some positive `lookDelta` when no enemy is
   visible. New tests should assert:
   - `lookDelta = 0` in the no-enemy straight-run case,
   - yaw changes only when a wall is within the probe distance,
   - the player covers more ground (e.g., distance from spawn increases over
     a few seconds).
4. **Integration with `castRayDDAFromFlatMap`.** That function is currently
   used by the renderer and may require a thin wrapper to expose a
   wall-distance-only probe without allocating render intermediates.
5. **Human mode isolation.** `buildFallbackAutoTickInput()` is only called in
   auto mode, but confirm the exploration state is not accidentally shared
   with human-mode input handling.

### Confidence

**Overall confidence: 0.90** | Provenance: direct static-code read of
`buildFallbackAutoTickInput`, `host/game/constants.ts`, `host/game/movement.ts`,
plus the asciiMaze exploration patterns reported by
`implementation-pattern-scout`. The geometric "circle" derivation is
algebraic and deterministic. The recommendation to start with Option A is a
pragmatic judgment, not a validated comparison.
